## Phase Goal

**As a** Kitcha user standing in my kitchen or a grocery aisle with a phone, **I want to** install Kitcha and use every screen comfortably with one thumb, in my own currency, **so that** I can quickly see what I have, what to cook and what to buy.

<objective>
Ship the backend contract the frontend slices depend on, test first: a server-side currency allow-list (express-validator `isIn` with an upper-case sanitizer) and onboarding completion state (`UserPreference.onboardingCompletedAt`, additive migration with backfill, idempotent `POST /api/v1/users/onboarding/complete`).

Purpose: MOB-06 needs the server to enforce valid currency codes (a bad code would crash `Intl` in the UI); MOB-05 needs onboarding state that follows the user across devices without forcing existing users through it.
Output: constants file, validation/service/controller/route/type changes, schema + migration, Jest tests.

Do NOT deploy or `git push` here. Plan 03-13 deploys this backend to Railway before the frontend is pushed.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> PATCH /users/preferences | untrusted currency string and body fields |
| client -> POST /users/onboarding/complete | authenticated, no body |
| migration -> production data | backfill UPDATE runs on deploy |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-04 | Tampering | currency field | mitigate | express-validator `isString` + `trim` + upper-case sanitizer + `isIn(SUPPORTED_CURRENCIES)`; tests for XXX/ZZZ/number |
| T-03-05 | Tampering | mass assignment of onboardingCompletedAt via PATCH | mitigate | updatePreferences keeps explicit field whitelist; field not in UpdatePreferencesRequest; test asserts PATCH cannot set it |
| T-03-06 | Elevation of privilege | onboarding endpoint IDOR | mitigate | route is after `router.use(authenticate)`; acts only on `req.user.id`, no id param; 401 test without token |
| T-03-07 | Repudiation/Tampering | client-chosen timestamp | mitigate | server stamps `new Date()`; updateMany only where null (idempotent, first value wins) |
| T-03-08 | Denial of service | endpoint spam | mitigate | existing `apiLimiter` on `/api/`; operation is a single indexed update |
| T-03-09 | Denial of service | migration on deploy | mitigate | additive nullable column + single UPDATE; no drift check; tested on TESTENV before deploy |
</threat_model>
