  <behavior>
    prefs:
    - parseReminderPrefs(undefined | garbage | {offsets: []} | {time:'09:15'}) returns DEFAULT_REMINDER_PREFS (invalid -> defaults); valid object round-trips
    - offsets deduplicated and sorted; time must be one of REMINDER_TIME_OPTIONS (30-minute steps)
    - toggleOffset removing the last remaining offset returns { blocked: true } with prefs unchanged; adding returns a new object (input frozen, not mutated)
    - snooze sets until now + 14 days; isReminderPromptSnoozed true before, false after; storage throwing -> not snoozed, no throw
    plan (run every case across the 4-zone TZ matrix):
    - item expiring in 2 days, offsets [1], time 09:00 -> one notification at local tomorrow 09:00, body "Milk expires tomorrow"
    - offsets [0] -> body "Milk expires today"; offsets [2] -> "Milk expires in 2 days"; offsets [3] -> "in 3 days"
    - three items same day -> one notification "3 items expire tomorrow: Eggs, Milk, Spinach" (names alphabetical)
    - five items same day -> "5 items expire tomorrow: A, B, C and 2 more"
    - fire time already past (e.g. offset 0, now 10:00, time 09:00) -> skipped
    - expired items, null/invalid expiryDate -> skipped
    - multiple offsets [0,1] -> separate notifications per (day, offset)
    - more than 60 groups -> exactly 60, earliest first
    - ids are REMINDER_ID_BASE + index (0..59), all pass isReminderId; title 'Kitcha'; route EXPIRING_ROUTE
    - item names trimmed, whitespace collapsed, truncated to 40 chars with an ellipsis
    - prefs.enabled false -> empty array
    - input array not mutated
    route:
    - { route: '/pantry/?filter=expiring' } -> that string
    - { route: 'https://evil.example' }, { route: '/settings' }, null, 'x', { route: 5 } -> null
    scheduler (vi.fn plugin mock, fixed now):
    - prefs.enabled false -> cancels Kitcha-owned pending ids, returns { status: 'disabled', scheduled: 0 }, never calls checkPermissions-gated schedule
    - checkPermissions 'prompt' / 'prompt-with-rationale' / 'denied' -> { status: 'not-granted' }, schedule NEVER called, requestPermissions NEVER called
    - granted -> getPending, cancel called with only ids where isReminderId (foreign id 5 untouched), then schedule with mapped notifications ({ id, title, body, schedule: { at: fireAt }, extra: { route } })
    - granted with empty plan -> cancel own ids, schedule not called, { status: 'scheduled', scheduled: 0 }
    - schedule rejecting -> { status: 'error' }, logged message only, no throw
    - two overlapping sync() calls run sequentially (second starts after first resolves)
    - clear() cancels only own ids; requestOptIn maps 'granted' -> 'granted', everything else -> 'denied'
    - checkPermission returns 'unknown' when plugin throws
  </behavior>
  <implementation>
Per CONTEXT decision "schedule expiry reminders on-device from pantry data (morning-of and N days before), opt-in permission flow, reschedule on pantry change; works in airplane mode" and UI-SPEC "Scheduling rule".

plan.ts: for each item, days = getDaysUntilExpiry(item.expiryDate, now); skip null or negative. Parse the YYYY-MM-DD date parts from the expiry string (reuse the same prefix format; extract a tiny helper) and for each offset build fireAt = new Date(y, m-1, d - offset, hh, mm) in LOCAL time (the OS fires in local time; airplane mode safe). Skip fireAt <= now. Group key = fire date (local YYYY-MM-DD) + offset. Body by offset: 0 "expires today"/"expire today", 1 "tomorrow", 2/3 "in N days"; single vs plural form per UI-SPEC ("Milk expires tomorrow" / "3 items expire tomorrow: Milk, Eggs, Spinach", 3 names then "and N more"). Sort groups by fireAt then key, slice to 60, assign ids. Return frozen objects.

scheduler.ts: DI factory in the style of session-refresh.ts; serialize sync calls with a promise chain; Pitfall 3: call checkPermissions FIRST and return early unless display === 'granted'; never call requestPermissions except from requestOptIn. Wrap every plugin call; errors logged with message only.

native-scheduler.ts: memoized `loadPlugin(() => import('@capacitor/local-notifications'))`, adapt `LocalNotifications` to LocalNotificationsLike (read the installed package's definitions to confirm method names and the permission field `display`), return createReminderScheduler({ plugin, now: () => new Date() }). addReminderTapListener registers 'localNotificationActionPerformed', runs parseNotificationRoute(event.notification.extra), calls onRoute only for allowed routes, and returns an unsubscribe function (no-op on web). No unit test for this file (thin glue; type-check covers it).
  </implementation>

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-12 | Tampering | parseNotificationRoute | mitigate | zod enum allowlist; anything else returns null and no navigation |
| T-10-13 | Information Disclosure | Notification body on lock screen | accept | Only item names (no account data, no quantities); sanitized and truncated to 40 chars; documented in summary |
| T-10-14 | Repudiation/Compliance | Unprompted permission request (Apple 5.1.2(i)) | mitigate | checkPermissions gate; requestPermissions only via requestOptIn; tests assert zero calls |
| T-10-15 | Denial of Service | Exceeding 64 pending iOS notifications | mitigate | Hard cap 60 in plan builder, tested |
| T-10-16 | Tampering | Corrupt reminder prefs in localStorage | mitigate | zod parse with defaults fallback |
